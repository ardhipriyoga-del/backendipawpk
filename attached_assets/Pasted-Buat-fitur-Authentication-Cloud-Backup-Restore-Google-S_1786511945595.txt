Buat fitur Authentication + Cloud Backup/Restore Google Spreadsheet untuk aplikasi existing ipawv2.html.

TUJUAN

Saya memiliki aplikasi ipawv2.html yang saat ini menggunakan penyimpanan lokal/IndexedDB.

Saya ingin menambahkan sistem:

Login → Verifikasi akun dari Google Spreadsheet → Restore data → CRUD → Auto Sync/Backup ke Google Spreadsheet

Jangan merusak fitur, UI, struktur data, dan fungsi existing IPAW v2.

⸻

ARSITEKTUR

Gunakan arsitektur:

ipawv2.html
↓
Backend API
↓
Google Spreadsheet

Backend dijalankan melalui Replit.

JANGAN mengakses Google Spreadsheet secara langsung dari browser.

Credential Google/API/service account harus disimpan sebagai environment variables / Secrets di Replit, bukan di HTML atau JavaScript frontend.

⸻

1. LOGIN

Buat endpoint:

POST /api/auth/login

Request:

{
  "username": "username",
  "password": "password"
}

Backend membaca sheet Users.

Contoh struktur:

id	username	password	nama	role	status
1	admin	xxx	Administrator	superuser	active
2	user01	xxx	User 01	officer	active

Jika username dan password sesuai dan status active:

Return:

{
  "success": true,
  "user": {
    "id": "1",
    "username": "admin",
    "nama": "Administrator",
    "role": "superuser"
  }
}

Jika salah:

{
  "success": false,
  "message": "Username atau password salah"
}

Jangan memberikan informasi apakah username atau password yang salah secara terpisah.

Jika memungkinkan, gunakan password hashing. Jangan menyimpan password plaintext pada implementasi production.

⸻

2. SESSION

Setelah login berhasil, buat session/token yang aman.

Frontend tidak boleh menganggap login berhasil hanya berdasarkan localStorage.

Setiap request API harus diverifikasi oleh backend.

Sediakan:

POST /api/auth/logout

dan:

GET /api/auth/me

⸻

3. RESTORE DATA OTOMATIS

Setelah login berhasil:

ipawv2.html harus otomatis memanggil:

GET /api/data/restore

Backend mengambil seluruh data IPAW dari Google Spreadsheet.

Data yang dikembalikan harus mencakup seluruh data yang diperlukan aplikasi, misalnya:

* pasien
* operan
* pending operan
* checklist
* billing
* master tarif
* konfigurasi
* activity log
* data user/workspace
* dan seluruh collection/store IndexedDB existing

JANGAN membuat struktur data baru jika struktur IndexedDB existing sudah tersedia.

Backend harus menyesuaikan dengan struktur data IPAW v2 yang sekarang.

⸻

4. RESTORE KE INDEXEDDB

Setelah response /api/data/restore diterima:

1. Validasi data.
2. Backup data lokal lama terlebih dahulu.
3. Clear/replace data IndexedDB sesuai kebutuhan.
4. Import data dari server.
5. Pastikan seluruh object store existing tetap kompatibel.
6. Setelah restore selesai, tampilkan status:

Data berhasil disinkronkan

Jika restore gagal, jangan menghapus data lokal existing.

⸻

5. CRUD AUTO BACKUP

Saya ingin setiap operasi CRUD IPAW dapat tersinkron ke server.

Buat API:

POST /api/data/create

PUT /api/data/update

DELETE /api/data/delete

Request minimal:

{
  "store": "nama_object_store",
  "id": "record-id",
  "data": {}
}

Setiap kali user melakukan:

* Create
* Update
* Delete

maka:

1. Update IndexedDB terlebih dahulu.
2. Tandai perubahan sebagai pendingSync.
3. Kirim perubahan ke backend.
4. Backend menyimpan perubahan ke Google Spreadsheet.
5. Jika berhasil → tandai synced.
6. Jika gagal → tetap simpan lokal dan masukkan ke sync queue.

⸻

6. OFFLINE-FIRST

IPAW tetap harus bisa digunakan ketika koneksi internet/server tidak tersedia.

Jika server tidak tersedia:

User CRUD
↓
IndexedDB
↓
Sync Queue
↓
Menunggu koneksi
↓
Auto Sync

Ketika koneksi kembali:

POST /api/sync

untuk mengirim semua perubahan yang masih pending.

Jangan sampai kegagalan internet menyebabkan data lokal hilang.

⸻

7. SYNC QUEUE

Buat sistem:

sync_queue

dengan informasi minimal:

id
operation
store
recordId
payload
createdAt
status
retryCount
lastError

Contoh:

{
  "operation": "update",
  "store": "patients",
  "recordId": "RM001",
  "payload": {},
  "status": "pending"
}

Gunakan retry otomatis.

Jangan membuat infinite loop.

⸻

8. AUTO SYNC

Tambahkan auto-sync setiap beberapa waktu, misalnya:

30–60 detik

Tetapi jangan melakukan request jika tidak ada perubahan.

Tambahkan juga tombol:

Sync Sekarang

Status UI:

* 🟢 Tersinkron
* 🟡 Menunggu sinkronisasi
* 🔵 Sedang sinkronisasi
* 🔴 Gagal sinkronisasi
* ⚫ Offline

⸻

9. GOOGLE SPREADSHEET STRUCTURE

Jangan menggunakan satu sheet besar untuk semua data jika itu membuat performa buruk.

Buat struktur yang mudah dikelola.

Contoh:

Users

Patients

Operan

Billing

Checklist

MasterTarif

ActivityLog

SyncLog

Jika IPAW v2 mempunyai object store lain, buat mapping otomatis.

Tambahkan kolom:

updatedAt

updatedBy

recordId

deleted

version

untuk kebutuhan sinkronisasi.

⸻

10. SOFT DELETE

Jangan langsung menghapus record penting dari Spreadsheet.

Untuk delete, gunakan:

deleted = true

Sehingga data masih dapat dipulihkan jika diperlukan.

Restore hanya mengambil data yang masih aktif, kecuali diperlukan untuk sinkronisasi.

⸻

11. CONFLICT HANDLING

Buat mekanisme conflict sederhana.

Setiap record mempunyai:

updatedAt
version
updatedBy

Jika ada perubahan dari dua perangkat/user:

* bandingkan updatedAt
* gunakan versi terbaru sebagai default
* catat conflict pada SyncLog

Jangan sampai data otomatis hilang karena conflict.

⸻

12. INITIAL SYNC

Saat user pertama kali login pada perangkat baru:

Login
↓
Auth berhasil
↓
GET /api/data/restore
↓
Restore seluruh data
↓
Masukkan ke IndexedDB
↓
IPAW siap digunakan

Jika IndexedDB sudah mempunyai data lokal, jangan langsung overwrite tanpa validasi.

Tampilkan proses:

Mengambil data cloud...

Memulihkan data lokal...

Sinkronisasi selesai

⸻

13. DATA SECURITY

WAJIB:

* Google credential hanya di Replit Secrets.
* Jangan expose service-account credential ke frontend.
* Jangan memasukkan API key Google ke ipawv2.html.
* Jangan menyimpan password user secara plaintext jika bisa menggunakan hashing.
* Validasi semua request di backend.
* User hanya boleh membaca/mengubah data yang memang menjadi haknya.
* Jangan percaya role, userId, atau username yang dikirim dari frontend.
* Ambil identitas user dari session/token backend.
* Tambahkan rate limit pada login.
* Jangan log password atau credential.
